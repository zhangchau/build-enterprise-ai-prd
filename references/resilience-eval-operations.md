## 1. 章节 13—19 的职责边界

| 章节 | 解决什么问题 | 不应写成 |
| --- | --- | --- |
| 13 异常 | 会出什么错，怎样发现和定位？ | 异常名词清单 |
| 14 降级恢复 | 错误发生时怎样安全继续并恢复？ | “失败转人工” |
| 15 安全 | 哪些边界不可被平均指标抵消？ | 合规口号和免责声明 |
| 16 评测 | 上线前怎样证明质量、风险、容量可接受？ | 一个总准确率 |
| 17 归因 | 指标变化为什么发生，改哪里？ | 只看相关性 |
| 18 Bad Case | 怎样修成以后不再同样发生？ | 截图收藏 |
| 19 运营 | 长期变化后怎样守住产品承诺？ | “持续迭代” |

关系：

`13 发现与诊断 → 14 止损/接管/恢复 → 15 守住红线 → 16 上线前 Gate → 17 线上归因 → 18 防复发 → 19 持续运营`

## 2. 统一异常排查

### 第一性原理

任何错误要做到：

1. 可检测；
2. 可限制影响；
3. 用户可理解；
4. 可交给正确的人；
5. 可恢复；
6. 可防复发。

### 排查链

`发现 → 固定现场 → 判断红线并止损 → 圈定范围 → 从前到后找第一处偏差 → 重放 → 根因与修复 → 回归 → 灰度 → 历史补处理 → 关闭`

固定：

- request/task/event；
- 用户、角色、tenant、权限版本；
- 业务对象和版本/hash；
- 输入、解析、规则、候选、上下文、输出；
- parser/rule/index/embedding/rerank/prompt/model/validator/workflow 版本；
- 人工和外部动作。

按顺序检查：

1. 输入/业务上下文；
2. 解析/结构/事实；
3. 规则/知识/权限；
4. Query/召回/Rerank/上下文；
5. Prompt/模型/Schema/业务校验；
6. Workflow/接口/缓存/状态；
7. 交互、用户理解和人工流程。

### 异常矩阵

| 类别 | 至少覆盖 |
| --- | --- |
| 输入 | 缺失、冲突、重复、超长、模糊、损坏、恶意 |
| 模型 | 幻觉、拒答、格式、超时、不可用、版本漂移 |
| 知识 | 不存在、无召回、低质、冲突、过期、投毒、泄漏 |
| 工具 | 失败、Unknown、重复、乱序、Schema 变化、长期不可用 |
| 权限 | 越权、脱敏失败、撤权缓存、租户缺失、数据出域 |
| 状态 | 处理中、旧结果、重复提交、并发修改、回滚 |
| 误用 | 草稿外发、把无召回当无风险、绕过人工 |
| Corner | 跨附件、多风险/一条款、后上传旧版、恢复时人已完成 |

每个异常用八格：现象、风险、检测、现场、立即处理、根因、长期修复、回归/关闭。

## 3. 降级、人工、恢复

### 机制定义

| 机制 | 目标 | 决策问题 |
| --- | --- | --- |
| Retry | 处理瞬时技术失败 | 是否幂等、次数和退避？ |
| Degrade | 保留安全能力子集 | 什么继续、什么必须停？ |
| Handoff | 让有责任的人接管 | 谁、带什么、做什么？ |
| Reconcile | 查清最终真实状态 | 系统、人工和第三方是否一致？ |
| Recover | 安全补跑/补写 | 是否仍需、同版本、已人工完成？ |
| Circuit Breaker | 防级联失败 | 何时开、半开、恢复？ |
| Rate Limit | 控制容量 | 谁优先、谁等待、怎样提示？ |
| Kill Switch | 停止不安全能力 | 最小范围和批准人？ |
| Rollback | 撤回坏版本 | 兼容、数据和历史影响？ |

### 降级矩阵

按组件写：

| 失败组件 | 可保留 | 必须关闭 | 用户提示 | 人工增量 | 恢复条件 |
| --- | --- | --- | --- | --- | --- |

例如 LLM 不可用时，若规则和原文证据可靠，可保留规则结果和人工任务；不得把缺失解释显示成“完整审查完成”。

### 人工六问

1. 什么信号触发？
2. 路由给哪个有决策权的角色？
3. 接手包带什么？
4. 人可以确认、修改、补件、驳回、升级或执行什么？
5. 结果写回哪个对象/版本，是否形成 Bad Case/知识候选？
6. 怎样审计，服务恢复后如何避免覆盖？

接手包：

- task/request、对象/版本、SLA；
- 原文、位置、附件、业务上下文；
- confirmed fact 与 candidate；
- rule trace、RAG evidence、AI 草稿；
- 失败节点、错误码、尝试和降级；
- 全链路版本；
- 历史人工/外部动作；
- 推荐下一步与允许按钮。

“上下文校准失败”不要作为模糊词。改写成具体原因，如：

- 缺关键业务字段；
- 证据冲突；
- 文档与附件关系不确定；
- 规则 scope 无法判断；
- 当前对象版本已变化。

### 恢复三问

1. 任务是否仍需处理？
2. 对象是否仍是相同版本？
3. 人工或第三方是否已经完成？

只重跑 `未完成 + 当前版本 + 可幂等重放`。旧任务标 stale，人工结果优先，Unknown 先查询/对账。

## 4. 安全与责任

### 四个目标

- **保密性**：不该看的人看不到；
- **完整性**：事实、规则、结果不被未授权篡改；
- **授权性**：建议、决策和执行由有权限主体完成；
- **可追责性**：能还原谁基于什么版本做了什么。

### 红线表

| 红线 | 攻击/失败输入 | 期望行为 | 检测证据 | Gate/事件动作 |
| --- | --- | --- | --- | --- |

覆盖：

- 跨租户/越权；
- 敏感出域；
- Prompt Injection/知识投毒；
- 虚构正式依据；
- 高风险错误放行；
- 未确认外部动作；
- 用户无法申诉；
- 评测/生产数据泄漏。

Prompt 防护不能只靠 System Prompt。使用输入不可信标签、检索权限、工具白名单、参数校验、输出 DLP、人工确认和审计。

### 责任矩阵

区分：

- AI 生成候选；
- 系统执行确定性校验；
- 产品定义状态、门槛和交互；
- 专家确认专业结论；
- 有权审批人承担例外/外部动作；
- 安全/平台承担访问和事件治理。

“AI 仅供参考”不能替代责任设计。

## 5. 评测集与发布 Gate

### 从 0 到 1

`任务卡 → 风险 → 数据 → Gold → 组件 → 专项 → 端到端 → 红队/故障 → 成本容量 → Gate → 影子/灰度`

### 数据来源

- 获授权的历史真实任务；
- 专家构造的规则边界；
- 线上 Bad Case；
- 反例和 hard negative；
- 无答案/冲突/权限；
- 红队和故障注入；
- 新分布探索集。

### 分布

同时覆盖：

- 典型、复杂、边界、失败、安全；
- 高/中/低风险；
- 角色、类型、语言、长短、扫描/电子；
- 新旧规则/知识；
- 有/无答案、冲突、过期、无权；
- 正常/降级/外部依赖异常。

不要只按自然线上比例抽样，高风险低频样本需挑战集保证覆盖。

### 数据集合隔离

| 集合 | 用途 | 规则 |
| --- | --- | --- |
| 开发/调优 | 迭代 | 可反复看，记录实验 |
| 验证 | 选型 | 有限使用 |
| 冻结发布 | Gate | 不逐题调优，严格版本 |
| 红队/安全 | 红线 | 独立权限，不进知识库 |
| 线上抽检 | 漂移 | 定期更新，与训练隔离 |

### Gold

包含：

- 输入和上下文；
- 原文 span/工具结果；
- 结构化事实；
- 适用规则/知识；
- 期望输出和允许变体；
- 应拒答/补问条件；
- 风险和错误严重度；
- 标注、复核和仲裁。

高风险双标/专家仲裁。无法唯一回答时定义可接受集合。

### 分层评测

| 层 | 评什么 |
| --- | --- |
| Parser | 字段、跨度、表格、关系、OCR 数字 |
| Rule | Recall/Precision、scope、冲突、边界、版本 |
| Retrieval | Recall@K、MRR/nDCG、权限、过期、hard negative |
| Generation | 证据支持、完整、引用、拒答、Schema、业务不变量 |
| Agent/Tool | 选择、参数、权限、终止、幂等、Unknown、恢复 |
| E2E | 任务完成、总周期、人工、返工、风险关闭、理解 |
| Safety | 红线、注入、泄漏、越权、错误执行 |
| Runtime | P50/P95/P99、并发、队列、恢复、单位成本 |

### Gate

每个 Gate 写：

- 指标和分层；
- 阈值来源；
- 样本/观察窗口；
- 未通过动作；
- 批准人；
- 回滚/缩范围。

示例：

- 红线事件确认即 No-Go；
- R1 质量未达则只允许人工确认；
- 人工队列无法承接则不扩量；
- P95/成本超预算则优化或缩场景；
- 业务任务未改善，即使模型分数升也不能全量。

数字没有测量时写“待试点基线后冻结”，不要发明。

## 6. 数据分析与归因

### 指标不是结论

看板分：

- 业务价值；
- 风险安全；
- AI 组件；
- 服务稳定；
- 人工运营；
- 成本。

必须按场景、风险、角色、输入质量、业务部门、版本和降级分层。

### 归因方法

1. 确认指标定义和数据管道；
2. 检查流量/用户/场景分布；
3. 对齐部署和知识/规则版本；
4. 沿 Trace 找第一个异常节点；
5. 用版本配对、消融替换或故障重放；
6. 结合人工原因码和 Case；
7. 小流量验证；
8. 输出决策、护栏和关闭标准。

### 防止成本转移

AI 节省法务时间但增加业务补件、运营标注或审批返工，不算完整成功。成对看：

- AI 处理时长 + 用户等待；
- 法务时间 + 业务准备时间；
- 自动通过 + 后续返工/事故；
- 模型成本 + 人工兜底/运营成本。

## 7. Bad Case 闭环

### 对象区别

| 对象 | 标准 |
| --- | --- |
| 反馈 | 主观感受，尚未验证 |
| Bad Case | 可重放且偏离明确期望 |
| 事故 | 红线、大面积或不可逆影响 |
| 需求 | 当前行为符合设计但需新能力 |

### 最小字段

- case/request、环境、时间；
- 用户/tenant/权限；
- 业务对象/版本；
- 输入、实际、期望；
- 全组件版本；
- 风险、外发/写回/人工状态；
- 临时止损、影响范围；
- 根因事实/假设；
- owner/SLA；
- 原/同类/反例/副作用回归；
- 灰度、历史补处理和关闭。

### 根因与修复

找第一处错误：

- 输入事实错 → Intake/确认；
- Clause/Fact 错 → Parser/结构；
- 确定规则错 → Rule；
- 知识存在但没召回 → Query/Chunk/Embedding；
- 候选有但排序错 → Filter/Rerank；
- Evidence 正确但输出不遵循 → Prompt/Model/Validator；
- 结论正确用户误解 → Interaction；
- 重复/错版本写入 → Workflow/幂等/对账。

每个 Case 形成：

1. 原样本；
2. 同类变体；
3. 反例/hard negative；
4. 副作用样本。

关闭需：风险受控、根因有证据、范围完整、回归/灰度通过、历史处理完成、临时措施有结论。

## 8. 上线运营与 Runbook

### 运营对象

规则、模板、案例、政策、评测、Prompt、模型、索引、Embedding/Rerank、权限、Workflow、工具、人工队列和成本。

每个对象必须：

`owner + version + source + status/effective + monitor + release Gate + rollback + recovery`

### 监控

形成：

`信号 → 分层 → 阈值依据 → 判断 → 动作 → owner → 升级 → 恢复`

告警关联同一上游故障，避免 parser 故障产生多条无关告警。红线不能普通静默。

### 节奏

| 节奏 | 看什么 | 产出 |
| --- | --- | --- |
| 实时/日 | P0/P1、服务、队列、成本 | 止损/恢复 |
| 周 | Bad Case、分层质量、知识、人工原因 | 修复/实验 |
| 月 | 业务价值、范围、版本、预算 | 扩量/收缩/替换 |
| 季度/重大变更 | 红队、灾备、供应商、数据权限 | 再认证/整改 |

### 变更发布

`提出/Why → 影响分析 → 分层回归 → 专业审批 → 影子/灰度 → Gate → 完整版本发布 → 监控 → 回滚/保持 → 历史影响处理`

完整版本矩阵：

`parser + rule_pack + knowledge_snapshot/index + embedding + reranker + prompt + model + validator + workflow + permission_policy`

### Runbook

| 字段 | 内容 |
| --- | --- |
| 触发 | 告警/反馈与确认方法 |
| 影响 | 租户、对象、版本、风险、外部动作 |
| 止损 | 开关、回滚、降级、人工、提示 |
| 排查 | Trace、版本、依赖、第一处偏差 |
| 恢复 | 条件、灰度、重试、对账、补审 |
| 沟通 | DRI、同步对象、频率 |
| 关闭 | 证据、历史影响、回归、复盘 |

## 9. 必做 Case 与面试追问

至少写：

1. 缺关键角色导致规则方向错误；
2. 证据存在但模型编造引用；
3. 相似案例来自相反角色或历史特批；
4. 外部写入超时但实际成功；
5. 老任务晚到覆盖新版本；
6. 撤权后缓存仍返回数据；
7. LLM 故障但规则仍可用；
8. 恢复时人工已处理；
9. 政策从 60 日变为 90 日；
10. 新模型 Schema 合法但业务含义漂移；
11. 成本翻倍来自重复上下文；
12. 知识下线但索引/缓存未删除。

面试回答结构：

`现象和风险 → 先止损 → 固定现场/影响范围 → 找第一处偏差 → Why 选此修复/Why not 其他层 → 原/同类/反例/副作用回归 → 灰度/对账/历史补处理 → 防复发`
