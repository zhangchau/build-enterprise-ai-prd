## 1. 文档服务对象

同一份文档要兼顾五类读者，但不能用同一种颗粒度混写：

| 读者 | 最需要回答 | 文档产物 |
| --- | --- | --- |
| 业务/用户 | 为什么做、改变什么、风险谁承担 | As-Is/To-Be、价值、范围、用户任务 |
| 产品/设计 | 具体功能、状态、权限、交互、异常 | 功能卡、状态机、原型说明 |
| 算法/数据/研发 | 输入输出、数据、Rule/RAG/LLM 边界、接口 | Schema、架构、任务卡、接口契约 |
| 法务/安全/运营 | 红线、人工、审计、发布、恢复 | 权限矩阵、Gate、Runbook |
| 零基础学员/面试官 | Why、取舍、迁移、真实性和个人判断 | 阅读提醒、练习、Decision Log、答辩卡 |

正文先完成产品和工程事实，再添加教学与面试层。不要为了“对小白友好”牺牲企业可执行性。

## 2. 第一性原理写法

任何实质设计都按以下链路推导：

`目标 → 当前障碍 → 可控变量 → 约束/错误成本 → 候选方案 → 选择依据 → 代价 → 失败信号 → 恢复 → 验证`

### 每节七问

1. **Why**：本节存在是为了让谁做什么决策？
2. **Why now**：为什么当前阶段需要，延后会怎样？
3. **Why not**：不做、人工、规则、搜索、RPA、较小模型或更简单流程为何不足？
4. **Know how**：角色、触发、输入、处理、输出、状态、权限、指标是什么？
5. **Failure**：怎样失败、如何发现、怎样止损和恢复？
6. **Evidence**：依据是什么，什么证据会推翻当前判断？
7. **Transfer**：换行业、数据、风险或规模后，哪些变量必须重评？

### Why not 的最低要求

至少比较当前方案与最强替代方案，禁止只写“模型更智能”。对每个候选写：

| 候选 | 能解决什么 | 不能解决什么 | 成本/风险 | 选择/不选依据 | 何时重评 |
| --- | --- | --- | --- | --- | --- |

## 3. 事实与证据纪律

### 五类陈述

| 标签 | 含义 | 可否写成项目成绩 |
| --- | --- | --- |
| 已确认事实 | 有用户、文档、日志、样本或系统证据 | 可以，附来源 |
| 有来源推断 | 由事实推导但未被业务确认 | 不可以，写推理链 |
| 待验证假设 | 为继续设计暂时设定 | 不可以，写验证动作 |
| 建议方案 | 面向未来的设计 | 不可以用过去式 |
| 待决策事项 | 需要 owner 权衡 | 不可以替 owner 决定 |

### 数字真实性

任何“提升 30%”“准确率 95%”“节省 2 小时”都要能回答：

- 指标定义、单位、分子、分母和排除项；
- 数据来源、样本、场景分层和时间窗；
- Ground Truth、基线、对照或前后版本；
- 归因、稳定性、Bad Case 和护栏；
- 是真实结果、试点结果、目标、行业参考还是示例。

没有证据时写：

- `目标值：待基线测量后确定`；
- `示例阈值，仅用于说明格式，不代表项目结论`；
- `课程项目假设，真实落地需由业务/安全/法务确认`。

### 个人职责

不要把算法训练、工程实现、法律裁决或生产结果写成产品经理个人完成。区分：

- 我负责定义/决策/协调/验收；
- 算法、研发、数据、安全、业务专家分别实现/确认；
- 有哪些可出示的 E3/E4 产物或结果。

## 4. 功能和技术深度

### P0 功能卡

每个 P0 功能至少包含：

| 维度 | 必填内容 |
| --- | --- |
| 身份 | 功能 ID、名称、优先级、owner、依赖 |
| 价值 | 用户、任务、目标、非目标、成功标准 |
| 进入 | 触发、前置条件、业务对象与版本 |
| 输入 | 字段、来源、必填、校验、权限、缺失处理 |
| 处理 | 主流程、规则、AI、人工、状态迁移 |
| 输出 | 字段、证据、版本、可见角色、下游消费 |
| 边界 | 异常、Corner Case、降级、恢复、并发/重复 |
| 交互 | 状态、危险动作、确认、撤销、反馈 |
| 数据 | 埋点、日志、指标口径、审计 |
| 验收 | 正常、异常、权限、边界和恢复 Case |

禁止只写“功能一：智能分析；功能二：自动生成；功能三：风险预警”。

### AI 任务卡

每个 AI 任务写：

- 输入、输出 Schema 和 Gold 单位；
- Rule/RAG/LLM/Tool/Human 的职责；
- 禁止行为和高风险错误；
- 数据来源、评测集、指标和阈值依据；
- 在线检测、失败状态、降级和人工；
- 版本、Trace 和回归资产。

### 确定性与概率性边界

优先用确定性机制承载：

- 权限、租户、数据出域；
- 企业正式规则、范围、优先级和生效；
- Schema、引用存在性、业务不变量；
- 外部写动作的确认、幂等和状态；
- 安全红线与发布 Gate。

LLM 适合承载：

- 非结构化理解、候选抽取；
- 证据范围内的解释、总结和改写；
- 多来源语义关联和自然语言交互。

LLM 不能成为权限系统、规则数据库或事务状态机。

## 5. 图、交互与原型

### 必须用图表达

适用时至少提供：

1. 业务 As-Is/To-Be；
2. AI 能力全景图；
3. 离线知识加工链路；
4. 在线 Rule + RAG + LLM 请求链路；
5. 关键调用时序；
6. 系统边界/信任域；
7. 异常排查或恢复；
8. 评测发布和 Bad Case 闭环。

图中标注：

- 节点 owner；
- 输入/输出对象；
- 存储位置；
- 同步/异步；
- 权限和信任域；
- 失败状态、降级和恢复。

图后用文字解释每条关键箭头的 Why，不要重复图中文字。

### 学员手画要求

每份教学文档至少出现一次显著提醒：

> 本图是信息结构参考。学员必须关闭示例后，基于自己的业务事实手画第一版，并能解释每个节点、箭头和失败分支。不要让 AI 代画最终图。

### 原型要求

没有真实原型时必须写：

> 当前暂不提供任何页面图片或高保真原型。企业真实落地时必须补可点击原型，并标注角色、入口、字段来源、状态、权限、危险动作、异常/恢复、埋点和验收。

禁止用 AI 生成的漂亮界面图冒充经过用户验证的原型。

## 6. Case 标准

结论后必须有 Case 帮助学员形成体感。Case 不是故事装饰，而是用来检验设计。

### 异常八格

| 字段 | 必答 |
| --- | --- |
| 用户现象 | 用户实际看到/做了什么 |
| 业务风险 | 不处理的后果 |
| 检测信号 | 系统如何主动发现 |
| 现场证据 | request、对象、权限、组件版本 |
| 立即处理 | 阻断、降级、回滚、转人工或对账 |
| 根因定位 | 第一处偏差在哪里 |
| 长期修复 | 修哪个组件、流程或职责 |
| 回归/关闭 | 原样本、同类、反例、副作用和历史补处理 |

### 好 Case 的特征

- 有具体角色、对象、版本、触发和状态；
- 能解释为什么表面现象可能来自不同根因；
- 包含错误做法与 Why not；
- 说明临时止损和长期修复的区别；
- 结尾让学员把变量替换成自己的项目。

## 7. 反套话规则

以下句子单独出现视为不合格：

| 套话 | 必须补充 |
| --- | --- |
| “优化 Prompt” | 哪个字段/失败、Evidence 是否正确、版本、评测和副作用 |
| “低置信转人工” | 置信来自哪层、风险、接手人、接手包、动作、队列、恢复 |
| “加强监控” | 指标、阈值依据、分层、动作、owner、恢复 |
| “使用 RAG 降低幻觉” | 数据、权限、切片、召回、重排、引用、无答案和评测 |
| “选择最先进模型” | 硬约束、候选池、任务集、指标、成本、主备和重评 |
| “做好安全合规” | 红线、攻击 Case、确定性控制、审计和事件流程 |
| “建立 Bad Case 闭环” | 收集、字段、分级、止损、归因、回归、灰度和关闭 |
| “上线后持续迭代” | 运营对象、owner、节奏、发布 Gate、回滚和 Runbook |

## 8. 完成度量表

每项 0—2 分：

| 维度 | 0 | 1 | 2 |
| --- | --- | --- | --- |
| 业务证据 | 口号 | 有问题无基线 | 问题、基线、损失、来源 |
| AI 必要性 | 技术先行 | 比较粗略 | 与强替代方案、边界和重评 |
| 功能 PRD | 功能名 | 主流程 | 字段、状态、权限、异常、验收 |
| 全链路 | 技术清单 | 局部流程 | 对象/版本/存储/调用/恢复贯通 |
| 数据/RAG | 结论 | 基本步骤 | 来源、治理、选型、评测和异常 |
| 评测 | 准确率 | 多指标 | 数据/Gold/分层/Gate/端到端/红线 |
| 治理 | 转人工 | 有降级 | 止损、接手、对账、补审和运营 |
| 教学迁移 | 给答案 | 有解释 | 阅读、练习、变量、面试追问 |
| 事实诚信 | 有编造 | 有标签 | 来源、证据等级和缺口完整 |
| 可答辩性 | 背稿 | 有 Why | 能应对约束变化并出示产物 |

任何事实诚信、安全红线或核心链路为 0，均不得判定企业可用。
