# build-enterprise-ai-prd

> 面向企业 AI 产品经理的长文档生产 Skill：从业务问题出发，分阶段产出可评审、可研发对齐、可验收、可复盘、可用于面试答辩的 AI 产品 PRD、方案决策与项目文档。

它不是“把 PRD 目录填满”的写作模板，而是一套把业务、产品、数据、模型、工程治理和运营闭环串起来的工作方法。适合从零搭建项目，也适合把已有的简版方案审计并扩展成企业实战级文档。

## 适用场景

- 从零完成 AI 产品课程项目、作品集项目或企业内部立项方案。
- 将短 PRD、产品方案、项目复盘扩展为完整的 AI 项目文档。
- 设计带有 Rule、RAG、LLM、Agent、工具调用或多模态能力的产品。
- 为 PoC、MVP、灰度、上线验收建立评测、降级、人工兜底、Bad Case 和运营机制。
- 准备 AI 产品经理模拟面试或正式面试的项目答辩材料。

## 不适用的情况

- 只需要一页需求说明、纯 UI 文案或普通非 AI 功能 PRD。
- 需要由法律、医疗、财务等持证专业人士给出最终结论的场景。本 Skill 可以帮助设计责任边界、证据引用和人工复核机制，但不能替代专业判断。
- 希望用虚构的访谈、上线数据、模型评测结果或个人职责包装项目。该 Skill 会把信息标记为“事实 / 推断 / 假设 / 建议 / 待决策”，而不是把假设写成成果。

## 你最终会得到什么

一份主文档，以及一个用于长期协作的轻量“外部记忆”工作区。

```text
合同审查_AI产品PRD方案决策与项目答辩文档.md
.合同审查_ai_prd_work/
├── project-brief.md        # 项目事实、一期场景、范围与风险
├── evidence-ledger.md      # 证据、假设、来源与验证缺口
├── decision-log.md         # 关键选择、Why / Why not、重评条件
├── context-snapshot.md     # 每批次压缩后的当前状态
└── state.json              # 批次与 Gate 的执行状态
```

主文档覆盖 0—22 章与附录，主要包括：

| 文档层 | 要回答的问题 |
| --- | --- |
| 业务与策略 | 谁在什么任务上受损？为什么此时要解决？为什么需要 AI，而不是规则、搜索或人工？ |
| 产品与体验 | 用户如何触发、输入、确认、编辑、反馈和申诉？每个 P0 功能如何验收？ |
| AI 与数据 | 业务任务如何拆为规则、RAG、模型、工具或人工？知识、权限、版本如何贯穿？ |
| 技术方案 | 模型、Embedding、Chunk、检索、Rerank、Prompt、Schema、Agent 和系统接口为什么这样选？ |
| 韧性与安全 | 异常、Corner Case、模型降级、人工接手、恢复、审计、隐私和越权如何处理？ |
| 评测与运营 | 如何构建 Gold、离线与端到端评测、红队、发布 Gate、归因、Bad Case 和回归闭环？ |
| 项目与答辩 | 资源、RACI、风险、决策记录、3/5/10 分钟讲解和面试深挖如何准备？ |

## 核心原则

1. **先业务，后 AI**：先明确用户、任务、损失、现有流程、风险和目标，再讨论模型。
2. **每个实质设计都回答 Why / Why not**：不仅说“怎么做”，还说明约束、替代方案、代价、失败条件与重评条件。
3. **事实诚实**：严格区分已确认事实、有来源推断、待验证假设、建议方案和待决策事项。
4. **链路完整**：把输入、规则、知识、检索、模型、结构化校验、人工、工作流、日志和评测连成同一条链路。
5. **失败可控**：正常流程之外，必须设计异常、降级、人工接手、对账、恢复和防复发。
6. **可交付、可验收**：功能写到触发、输入、状态、权限、异常、埋点和验收 Case；指标写到数据、Gold、阈值、Gate 和未通过动作。
7. **面试可追溯**：任何“我为什么这样做”的回答，都应能追溯到业务证据、Decision Log、评测报告或明确假设。

## 快速开始

### 1. 安装

将仓库放入 Codex 的本地 Skills 目录（已有同名目录时请先备份或更新，而不是直接覆盖）：

```bash
git clone https://github.com/zhangchau/build-enterprise-ai-prd.git \
  "$HOME/.codex/skills/build-enterprise-ai-prd"
```

重新打开或刷新 Codex 后，即可在对话中调用：

```text
使用 $build-enterprise-ai-prd，基于我的项目资料分阶段生成企业级 AI PRD、方案决策与面试答辩完整文档。
```

也可以直接描述目标，例如：

```text
请用 build-enterprise-ai-prd，基于“企业采购合同审查”场景，先建立真实/模拟事实边界，
再输出一期 MVP 的完整项目文档。项目用于课程评审和面试，尚无真实上线数据。
```

### 2. 创建文档骨架（可选，但推荐）

脚本不会覆盖现有文件。以下命令会基于内置母版创建 0—22 章文档及工作区：

```bash
cd build-enterprise-ai-prd

python3 scripts/init_prd_project.py \
  "AI 合同审查与谈判辅助平台" \
  --output-dir "/你的项目目录" \
  --mode guided \
  --project-type course
```

常用参数：

| 参数 | 说明 |
| --- | --- |
| `--output-dir` | 主文档与工作区的输出目录，默认当前目录。 |
| `--filename` | 自定义主文档文件名；只能传文件名，目录请用 `--output-dir`。 |
| `--mode` | `guided`、`autopilot`、`audit` 或 `pack-only`。 |
| `--project-type` | `real`、`course`、`simulation` 或 `unspecified`。 |
| `--source` | 已有资料路径；可重复传入，用于登记资料来源。 |

### 3. 按批次完成，而非一次性生成全文

Skill 以文件为外部记忆，避免长文档在单轮对话中失控。建议按以下节奏推进：

| 批次 | 章节 | 冻结的关键决策 |
| --- | --- | --- |
| B0 | 0—1 | 项目性质、事实边界、一期场景、文档用途 |
| B1 | 2—5 | 问题定义、AI 必要性、目标、MVP 与非目标 |
| B2 | 6—8 | 用户旅程、P0 功能、AI 子任务、输入输出和人工边界 |
| B3 | 9—12 | 数据/RAG、模型、Prompt/Agent、架构、权限与接口 |
| B4 | 13—16 | 异常、Corner Case、降级、人工恢复、安全、评测 Gate |
| B5 | 17—19 | 埋点、归因、Bad Case、监控、运营与迭代 |
| B6 | 20—22 + 附录 | 计划、成本、Decision Log、答辩和证据索引 |

`guided` 模式只在四个里程碑请求确认：

1. **Gate 0：生产契约**——项目是真是假、证据有什么、一期做什么。
2. **Gate A：策略**——问题、AI 必要性、MVP 与非目标。
3. **Gate B：方案**——功能、Rule/RAG/LLM/Tool 边界、架构和人工责任。
4. **Gate C：发布**——安全红线、评测、降级、运营与最终答辩版。

## 四种工作模式

| 模式 | 适合谁 | 协作方式 |
| --- | --- | --- |
| `guided`（默认） | 从零开始、资料不完整或需要教学引导 | 在 4 个 Gate 确认，不逐章打断。 |
| `autopilot` | 需要先快速形成“假设版”全案 | 除核心范围、责任和安全阻塞外，标注假设后持续推进。 |
| `audit` | 已有 PRD、方案或复盘文档 | 先给问题地图和修改批次，再针对原文补缺、修订。 |
| `pack-only` | 内容和决策已确认 | 整理为完整可读文档，仍执行内部校验和追溯检查。 |

## RAG、Embedding 等技术内容放在哪里？

技术内容不会被孤立地堆在“技术方案”章节，而是先由业务任务决定是否需要，再落到对应设计层。

| 问题 | 文档位置 | 需要形成的决策证据 |
| --- | --- | --- |
| 为什么需要知识检索，而不是关键词搜索或人工查询？ | 4、8、9.1 | 任务特征、知识时效/权限、传统方案对比、MVP 取舍。 |
| 文档如何解析、清洗、切片、向量化、建索引与回滚？ | 9.3—9.7 | 输入输出契约、版本、权限元数据、失败恢复、成本与时延。 |
| Embedding 选什么模型、为什么不选其他？ | 9.6 | 候选池、独立 Query 集、Recall@K、引用准确率、成本、部署与重建策略。 |
| 如何召回、重排、组装上下文、生成引用并校验答案？ | 9.8—9.11 | 离线/在线链路图、阈值、无召回策略、评测集和监控。 |
| 大模型、Prompt、微调、RAG、规则如何分工？ | 8、10、11 | 每类能力的输入输出、约束、失败模式、人工边界。 |
| 模型/API/向量库不可用时如何保证业务可继续？ | 13—16、19 | 降级状态机、接手包、对账、熔断、回滚、发布 Gate。 |

关键原则：**Embedding 不是一个“模型名字”，而是离线知识链路中的一个可替换组件。** 因此选型必须同时说明 Chunk、Metadata、权限过滤、索引、召回、Rerank、上下文组装和端到端任务效果，不能只报一个向量维度或排行榜分数。

## 典型调用示例

### 从零创建课程项目

```text
使用 $build-enterprise-ai-prd。

项目：面向企业法务的 SaaS/云服务采购合同审查助手。
性质：课程模拟项目；没有真实企业访问权和上线数据。
一期用户：采购法务在合同初审时识别高风险条款并给出证据引用。
约束：合同不得出域；AI 不得自动修改合同或替代法律结论。
已有资料：一份合同样本、公司条款红线、课程调研问卷。
用途：课程评审 + AI 产品经理面试。

请先完成 Gate 0 的生产契约和 B0，再列出需要我确认的 1—3 个关键问题。
```

### 审计已有 PRD

```text
使用 $build-enterprise-ai-prd 的 audit 模式，审计以下 Markdown 文档。
目标：找出业务证据、功能级 PRD、RAG 链路、异常降级、评测、Bad Case、运营和面试答辩的缺口；
先输出问题地图与修改优先级，再分批直接修订文档。不要把我的假设写成上线事实。
```

### 只深化 RAG 方案

```text
使用 $build-enterprise-ai-prd，补全现有文档的第 9 章。
请围绕“合同条款与内部红线库的可追溯问答”设计：
知识源与权限、解析清洗、Chunk、Embedding 选型、向量库与 Metadata、混合检索与 Rerank、
引用校验、更新/重建/回滚、异常降级和 Recall@K/引用准确率等验收指标。
每项都写 Why / Why not、假设、验证方法和面试追问。
```

## 文档质量与验收机制

### 功能级 PRD 的最低颗粒度

每个 P0 功能至少应包含：

- 功能 ID、用户任务、目标和非目标；
- 触发条件、前置条件、输入来源和主流程；
- 规则 / AI / 人工的职责划分；
- 输出、状态机、权限、交互提示和可编辑性；
- 异常、降级、恢复和人工接手；
- 埋点、验收 Case、依赖和 Owner。

### AI 评测至少三层

| 层级 | 示例关注点 |
| --- | --- |
| 组件离线评测 | 分类准确率、Recall@K、引用准确率、结构化输出合规率、拒答正确率。 |
| 端到端体验评测 | 任务完成率、人工修改率、用户满意度、首响/全程时延。 |
| 安全与韧性评测 | 越权、隐私泄露、提示注入、编造、高风险误导、超时、工具重复执行。 |

每项指标必须给出：评测数据与分布、Gold 或判定规范、阈值来源、评测频率、未通过 Gate 时的动作与 Owner。没有真实数据时，应标为目标值或待验证假设，不能伪装为线上结果。

### 内置确定性校验

完成主文档后运行：

```bash
python3 scripts/validate_prd.py "/你的项目目录/项目文档.md"
python3 scripts/validate_prd.py "/你的项目目录/项目文档.md" --strict
```

校验器会检查：

- 0—22 章与附录的基本结构；
- 未替换的明显占位符；
- 关键章节的覆盖度，例如 RAG、异常、降级、评测、Bad Case 与运营；
- Mermaid 图、教学提醒与关键可追溯要素。

它是结构和覆盖度检查，不等同于业务正确性、法律合规审查或真实模型效果验证。应先修复 `ERROR`，再逐一判断 `WARN` 是否合理；母版中的待填写占位符产生警告属于预期。

## 使用建议

- **把项目事实先放进 `project-brief.md`。** 哪怕只是模拟项目，也应清楚写出哪些是题设、哪些是研究推断、哪些是待验证方案。
- **一个版本只做一个可闭环的一期场景。** “做一个全能企业智能助手”不是可评测的 MVP；“采购法务在初审时识别 SaaS 合同中的高风险责任条款”才是。
- **Decision Log 不要事后补写。** 每次作出“选择 A、放弃 B”的决定，都记录依据、代价和重评条件。
- **原型、流程图必须自己理解后重画。** 文档可以给 Mermaid 结构参考，但面试中应能解释每条数据流、每个状态和每个人工确认点。
- **技术名词必须能回到业务任务。** 如果无法说明“它减少了哪类错误、怎么评测、失败后谁接手”，就不应为炫技而加入 RAG、Agent 或微调。
